# فاز چهار — اتصال میزها و رزرو

## اصل بنیادین
Viewer فقط سطح بصری است. دیتابیس و API رزرو فعلی Mizo تنها منبع حقیقت وضعیت و رزرو میز هستند.

## ابزار مدیر کافه

در پنل مدیریت صحنه:
- انتخاب میز موجود از فهرست میزهای شعبه
- قرار دادن marker روی موقعیت میز در محیط
- تنظیم موقعیت، چرخش و مقیاس marker
- اتصال میز به zone مانند indoor/terrace
- پیش‌نمایش از دید مشتری
- ذخیره نسخه draft
- تأیید و انتشار موقعیت‌ها

اگر میز در دیتابیس موجود نیست، ابتدا از جریان مدیریت میز فعلی ساخته شود؛ این ابزار نباید میز مستقل و ناسازگار ایجاد کند.

## نمایش مشتری

- marker میز فقط در فاصله یا حالت مناسب ظاهر شود.
- انتخاب marker پنجره جزئیات میز را باز کند.
- ظرفیت، zone و امکانات از دیتابیس فعلی دریافت شوند.
- تاریخ و ساعت انتخابی مشتری به API رزرو موجود ارسال شود.
- پاسخ API وضعیت را تعیین کند.
- در صورت تغییر وضعیت، UI به‌روزرسانی شود.
- وضعیت رزرو هرگز فقط از cache یا metadata صحنه نتیجه‌گیری نشود.

## هم‌زمانی و جلوگیری از double booking

- endpoint رزرو فعلی باید تراکنش و constraint مناسب داشته باشد.
- دو درخواست هم‌زمان برای یک میز و بازه نباید هر دو موفق شوند.
- بررسی availability و ثبت نهایی باید در backend انجام شود.
- idempotency key برای submit تکراری در نظر گرفته شود.
- Viewer نباید منطق رزرو را در کلاینت پیاده‌سازی کند.
- در خطای شبکه، وضعیت رزرو نامشخص تلقی و از سرور استعلام شود؛ پیام موفقیت زودهنگام نمایش داده نشود.

## مختصات و نسخه صحنه

هر `table_scene_position` باید به `scene_version_id` متصل باشد. هنگام انتشار نسخه جدید:
- موقعیت‌های قبلی حفظ شوند.
- اگر coordinate system تغییر کرده، تبدیل یا تأیید مجدد لازم باشد.
- نسخه جدید تا تأیید مدیر فعال نشود.
- rollback به نسخه قبلی ممکن باشد.

## تست‌ها

- میز indoor و terrace
- میز غیرفعال
- میز حذف‌شده از سیستم اصلی
- دو کاربر با درخواست هم‌زمان
- تغییر زمان در حین انتخاب میز
- انتشار نسخه جدید صحنه
- دسترسی بین دو کافه
- موقعیت marker در موبایل و دسکتاپ

## معیار پذیرش

مشتری بتواند میز درست را در محیط پیدا کند و رزرو را از مسیر اصلی Mizo تکمیل کند؛ تست هم‌زمانی نشان دهد رزرو تکراری ثبت نمی‌شود.
